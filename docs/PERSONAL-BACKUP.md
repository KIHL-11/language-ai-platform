# Personal 学习数据的备份与恢复

本文说明如何备份 Personal 模式的学习数据、如何校验备份，以及如何在隔离目录中做恢复演练。

工具：`backend/scripts/personal_backup.py`。逻辑代码在 `backend/services/backup/personal.py`。

## 备份的内容

备份的对象是 `backend/storage/` 下所有的普通文件：

- `learning_library.json` 和 `library_media/`：课程、收听进度和音频；
- `study_bank.json`：Study Bank，以及 SRS 复习状态；
- `speaking_sessions.json`：口语练习和 Topic Mock 的记录；
- `chunk_bank.json`：chunk memory；
- `dictionary.sqlite3` 等 SQLite 文件。

**下面两类文件不在备份范围内**，需要另外处理：

- `DICTIONARY_DB_PATH` 或 `DICTIONARY_FORMS_INDEX_PATH` 指向的、位于 storage 目录**之外**的词典文件。
- `backend/media/` 中的临时媒体。

## 使用边界

本工具只按下面的前提设计和测试。超出这些前提时，下文的各项检查不能当作安全保证：

- **可信的单用户 Mac。** 运行备份或恢复时，不应有其他不可信的进程以同一个系统用户的身份运行。
- **先停服。** 备份前，Owner 必须手动停止应用。
- **离线恢复。** 恢复只写入一个新的、隔离的目录，用来检查。把数据放回实时 storage，必须由 Owner 在停服之后手动完成（见下文“使用方法”）。

## 安全性质

- **停服是人工前提。** 必须先由 Owner 手动停止应用，并在命令行中显式传入 `--confirm-app-stopped`。工具还会探测 loopback 端口（IPv4 的 `127.0.0.1` 和 IPv6 的 `::1`），有服务在监听时拒绝执行。但这个探测只是**额外的、尽力而为的拒绝**，端口没有监听**不能证明**应用已经停止（应用可能在别的端口或接口上，也可能正在写入）。
- **只读取真实数据。** 对 storage 只做读取和字节复制，不会直接打开实时的 SQLite 数据库（SQLite 即使以只读方式打开，也可能生成 `-wal` 和 `-shm` 文件）。
- **复制校验。** 每个文件复制完成后，都会从磁盘重新计算 SHA-256，并与复制时读到的字节比较。复制期间如果有源文件的大小或修改时间发生变化，这次备份会被整个丢弃。
- **SQLite。** 先把数据库文件和它的日志文件按字节复制到私有的临时目录，再从这份副本执行 SQLite 的 backup API，生成一个单文件数据库。结果必须通过 `integrity_check`，并且逻辑内容（`iterdump` 的摘要）必须与副本一致。
- **完整性。** 备份先写入 `.partial` 目录，生成 SHA-256 的 `MANIFEST.sha256`，执行 fsync，再用不覆盖目标的原子重命名，改名为正式目录，因此已有的备份不会被覆盖。任何一步出错，工具都会尝试删除 `.partial` 目录。如果删除本身失败，`.partial` 目录可能残留（工具不会单独报告这种情况），需要人工检查备份目录。
- **恢复先写入独立的 staging 目录，全部通过后才发布。** 恢复时，数据先复制到目标旁边的私有 staging 目录，然后依次检查：
  1. 每个文件都要重新计算 SHA-256，文件集合和哈希值都必须与备份的 MANIFEST 完全相同；
  2. 用应用自己的 store 类重新读取数据，并与备份时生成的摘要比较，包括：
     - 课程和学习进度；
     - SRS 状态；
     - 口语记录及其事件数；
     - chunk memory；
     - SQLite 的完整性检查结果、每张表的行数和逻辑摘要；
  3. 读取完成后再核对一次哈希，确认读取过程没有改动任何文件。

  全部通过之后，才把 staging 目录重命名为目标目录。出错时，工具不会发布目标目录，并会尝试删除本次在 staging 中创建的内容。下面两类条目会留在原处，并在错误信息中列出：不是本次创建的条目，以及删除失败的条目。这时需要人工检查和清理（见下文“威胁模型”）。
- **只使用一次校验的结果。** MANIFEST 只读取一次，`backup.json` 也直接从计算哈希时读到的那份字节中解析。恢复只使用这一次校验得到的条目，不会再读取任何未经校验的版本。
- **路径安全。** 下列路径都会被拒绝：绝对路径、`..` 或 `.` 组成的路径、空的路径段、反斜杠、NUL 和其他控制字符，以及 `storage/` 之外的路径。备份中任何一级路径（包括文件本身）是符号链接时，也会被拒绝。恢复只向私有的 staging 目录写入。有同 UID 进程并发修改时的情况，见下文“威胁模型”。
- **恢复时的目录约束（基于目录描述符）。** staging 根目录以 0700 权限创建，然后用 `O_DIRECTORY|O_NOFOLLOW` 打开，之后的所有操作都相对于已经打开的描述符进行：
  - 每一级子目录都在已打开的父目录描述符下 `mkdir`，再以 `O_NOFOLLOW` 打开。任何一级是符号链接或被替换成其他对象，都会被拒绝。
  - 每个文件都以 `O_CREAT|O_EXCL|O_NOFOLLOW` 相对于已打开的目录描述符创建，写入和复核都通过同一个描述符完成，不会按路径重新打开。
  - 读取备份源文件同样逐级使用描述符，并且要求内容的哈希等于 MANIFEST。
  - 校验恢复结果时，从 staging 根目录描述符开始遍历，要求可达的文件集合与本次创建的 inode 完全一致，并通过描述符计算哈希。
  - 发布时，相对于父目录描述符执行不覆盖的重命名（Linux `renameat2`，macOS `renameatx_np`）；重命名前后都核对 staging 名称对应的仍是本次的根目录 inode。
  - 失败时只尝试删除本次创建的 inode（按 dev/inode 核对后再删除）。不是本次创建的文件和目录，不会被删除，而是在异常说明中列出。
- **威胁模型。**
  - *其他用户（不同 UID）的普通进程*：staging 目录是 0700，在常规权限下无法进入。root，以及有相应权限的进程不受这个限制。
  - *同一 UID 的并发进程*：它可以对 staging 树执行任意的重命名、替换和移动。`O_NOFOLLOW` **不能**阻止它把一个已经打开的目录移到 staging 之外（描述符会跟着目录走）。本工具的做法是**检测、尝试回撤、失败关闭**：
    - 每次创建文件前后，以及发布前，都从父目录描述符开始逐级核对 inode 链。
    - 发布后再核对一次。如果发布出去的不是本次的目录，就尝试把它挪到 `.<target>.rejected-*`，然后报错。
    - 检测到异常之后，会尝试通过描述符删除本次已经写入的文件，包括已经被移到外面的目录中的文件。
  - **剩余限制**：
    - 在“检查”和“创建”之间的极短窗口内，如果一个同 UID 进程把目录移走，那次写入会**短暂地**落在 staging 之外，之后才会被检测到并尝试删除。
    - 同样，在发布前的检查和重命名之间替换 staging 的名称，被替换进来的目录会被短暂发布，之后再尝试撤下。
    - 回撤本身也可能失败，例如条目再次被移动，或者权限发生了变化。这时工具会在错误信息中报告残留的条目，需要人工检查 staging 所在目录和目标目录。
    - 本工具**不能**作为对抗同 UID 恶意进程的安全边界。同 UID 进程本来就能直接修改该用户的所有文件。这也是上文“使用边界”要求在可信的单用户环境中使用的原因。
  - 不支持目录描述符相关操作的平台，会在写入任何内容之前失败关闭（`ContainmentUnsupported`）。
- **原子发布，不覆盖已有目录。** 发布时使用内核级的、不覆盖目标的原子重命名：Linux 上用 `renameat2(RENAME_NOREPLACE)`，macOS 上用 `renameatx_np(RENAME_EXCL)`。如果目标在发布的那一刻被别人创建（包括一个空目录），工具会拒绝执行，不会覆盖它。如果撤下错误发布的目录失败，工具会报告，需要人工检查。其他平台，以及不支持这种重命名的文件系统，都会失败关闭。
- **恢复目标的限制。** 恢复的目标目录不能是实时 storage 目录，也不能在它里面；目标目录必须是新的，不能已经存在。
- **格式版本。** 备份格式为 `language-ai-personal-backup/2`，`/1` 格式的备份会被拒绝。

## 使用方法

先停止应用，然后在 `backend/` 目录下执行：

```bash
python scripts/personal_backup.py backup --confirm-app-stopped --dest "/Users/<you>/备份/语言网站/personal-data"
```

```bash
python scripts/personal_backup.py verify --backup "/Users/<you>/备份/语言网站/personal-data/personal-backup-<stamp>"
```

```bash
python scripts/personal_backup.py restore --backup "<backup>" --target "/tmp/restore-check-<stamp>"
```

退出码：0 表示成功；2 表示被拒绝或者校验失败。

**把恢复出来的数据放回实时 storage，不由本工具完成。** 这一步需要在停止应用之后，由 Owner 手动操作。操作之前，先对当前的 storage 再做一次备份。

## 测试

`backend/tests/test_personal_backup.py`，只使用合成数据。覆盖的情况：

- BK-1：备份完整，并且可以校验；
- BK-2：恢复后读取到相同的记录和 SRS 状态；
- BK-3：服务运行时拒绝备份；
- BK-4：任何一个字节被篡改，校验都会失败，恢复也会被阻止；
- BK-5：已有的备份不会被覆盖，备份目标也不能在 storage 之内；
- 复制期间 storage 发生变化时，备份被丢弃；
- storage 中有符号链接时拒绝备份；
- SQLite 的 WAL 中尚未写回主文件的内容，也能被备份；
- storage 为空时，也可以正常备份和恢复；
- 命令行工具的完整流程。

此外，每个测试都会检查实时 storage 中所有文件的 SHA-256 和修改时间都没有变化。
